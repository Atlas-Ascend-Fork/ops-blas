# Ctrmv Test - Ascend C Kernel

## Overview
This test implements the `aclblasCtrmv` operator on Ascend 950PR (arch35) using Ascend C kernel.
The operator computes the single-precision complex (complex64) triangular matrix-vector product
`x = op(A) * x` in place, where `op(A)` is `A` (OP_N), `A^T` (OP_T) or `A^H` (OP_C, conjugated).
Semantics align with cuBLAS `cublasCtrmv` / Netlib `ctrmv`.

- A is an n×n column-major triangular matrix stored in full (lda×n); only the triangle selected
  by `uplo` is referenced, the other triangle is never read.
- `diag = ACLBLAS_UNIT` treats the main diagonal as 1 and does not access A's diagonal storage.
- x is read in place and overwritten with the result; any nonzero stride `incx` (including
  negative, reverse traversal) is supported.
- `n = 0` is a valid no-op returning `ACLBLAS_STATUS_SUCCESS`.

## Test Structure
- `test/trmv/ctrmv/ctrmv_param.h` - Parameter structure parsed from CSV (uplo/trans/diag/n/lda/incx + a_fill/x_fill)
- `test/trmv/ctrmv/ctrmv_golden.h` - CPU reference via Netlib `cblas_ctrmv`
- `test/trmv/ctrmv/ctrmv_npu_wrapper.h` - NPU wrapper (H2D copy, in-place API call, D2H copy)
- `test/trmv/ctrmv/arch35/ctrmv_test.cpp` - GTest parameterized test (CSV-driven)
- `test/trmv/ctrmv/arch35/ctrmv_test.csv` - 1200 test case definitions
- `test/trmv/ctrmv/CMakeLists.txt` - CMake configuration (arch35 uses CSV+GTest registration)

## Test Cases
The CSV (`ctrmv_test.csv`) contains cases with columns:
- `case_name` / `description`: Test case identifier / description
- `uplo` / `trans` / `diag`: Fill mode enums (all 12 combinations covered)
- `n`: Matrix dimension (0, 1, primes, powers of 2 ±1, non-aligned, up to 2048; perf up to 4096)
- `a_fill` / `x_fill`: Fill modes (RANDOM_NORM_5_5, RANDOM_ALTER, RANDOM_EXTREME, RANDOM_NAN_OFFTRI, VALUE_NORM_0/INF/NAN, NULLPTR)
- `lda`: Leading dimension (compact `n` and padded `n+8`)
- `incx`: Strides (nonzero, can be negative; 0 → INVALID_VALUE)
- `expect_result`: Expected aclblasStatus_t
- `random_seed`: Reproducibility (seeds the RANDOM_* generators)

Coverage categories:
- L0 basic (12), SQ size scan (69), LD leading-dim padding (9), INC stride combos (18),
  FL fill (16), CV coverage (48), ED edge/negative (11), EX extended (821), PF perf (200)

Negative cases map 1:1 to the task spec §2.4 abnormal behaviors: null A/x → INVALID_VALUE,
invalid uplo/trans/diag enums → INVALID_ENUM, lda < max(1,n) / n<0 / incx=0 → INVALID_VALUE,
n=0 quick-return → SUCCESS.

## Precision Verification
- Output is a COMPLEX64 vector: real/imag parts are verified separately per FLOAT32 standard
  (task §3.2): per-element `|actual-golden| ≤ atol + rtol×|golden|` with rtol=2^-10, atol=2^-16,
  matched_ratio ≥ 0.99 and max_abs_error ≤ max(1e-2, 32×ULP).
- Golden generated by Netlib `cblas_ctrmv` (single precision), matching the task requirement.
- Special-value cases (VALUE_NORM_INF / VALUE_NORM_NAN) are judged by the framework
  MixedToleranceStrategy: an element is skipped only when actual and golden are exactly
  equal or both NaN; any one-sided Inf/NaN fails hard (see test/frame/verify.h). With
  these fills every partial sum degenerates to NaN/Inf regardless of accumulation order,
  so NPU and cblas golden match element-wise.
- RANDOM_NAN_OFFTRI cases poison every cell ctrmv must not read (opposite of the
  selected triangle, plus the diagonal when diag=UNIT) with NaN via
  `CtrmvPoisonUnreadTri` (ctrmv_fill.h), proving only the selected triangle is
  accessed and a unit diagonal is never read.
- EXTREME/ALTER fill ranges were bounded to values the ecosystem 32×ULP limit can still judge
  (see ctrmv_fill.h); FLT_MAX-scale fills would overflow products to INF/NaN whose landing
  pattern depends on accumulation order and is not comparable across implementations.
